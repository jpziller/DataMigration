# NPC Fundraising — Sample Dataset

A fully **synthetic** Nonprofit Cloud (AFNP) fundraising / donor-management
dataset spanning the platform's full fundraising object surface (20 objects).
It exists so anyone who clones this repo can load a **fresh test / scratch org**
with a realistic, relationship-consistent set of records — to exercise the
migration framework end to end, demo it, or validate target-org behavior —
**without any real client data**.

> Nothing here is real. Every value is generated by [Snowfakery](https://github.com/SFDO-Tooling/Snowfakery)
> (Salesforce's own synthetic-data engine) from `describe()`-derived field
> schemas. Safe to load anywhere you have permission to write.

## What it contains

| Build group | Object(s) | Approx. rows | Generated by |
|---|---|---|---|
| 1 | Household Account + Contact | 8 households, ~13 contacts | `recipes/01_household_accounts_and_contacts.recipe.yml` |
| 2 | AccountContactRelation, PartyRelationshipGroup, ContactContactRelation | derived | pure SQL (no generation) |
| 3 | Organization Account | 5 | `recipes/02_organization_accounts.recipe.yml` |
| 4 | Person Account | 10 | `recipes/03_person_accounts.recipe.yml` |
| 5 | ContactPointAddress / Phone / Email | 35 each | `recipes/04–06_*.recipe.yml` |
| 6 | Campaign + CampaignMember | 4 campaigns, ~20 members | `recipes/07_campaigns_and_members.recipe.yml` |
| 7 | GiftDesignation | 6 | `recipes/08_gift_designations.recipe.yml` |
| 8–9 | GiftCommitment (+ GiftCommitmentSchedule) | 15 | `recipes/09_gift_commitments.recipe.yml` |
| 10 | GiftTransaction + GiftRefund + GiftSoftCredit | 40 txns, ~0–1 refund/soft-credit each | `recipes/10_gift_transactions_refunds_softcredits.recipe.yml` |
| 11 | GiftDefaultDesignation, GiftTransactionDesignation | derived | pure SQL (no generation) |

Groups 2 and 11 generate **no** mock data — those objects are derived by SQL
from already-loaded records, or are platform auto-created (see the notes at the
bottom). The recipes are numbered to match this build order.

## How the pipeline works

```
Snowfakery recipe ──▶ <Object>_Mock table ──▶ SQL transform ──▶ <Object>_Load table ──▶ bulkops ──▶ target org
   (recipes/)          (mirror DB)              (sql/transformations/230–430)             (Bulk API 2.0)
```

The mock data is only the *starting* raw material. The numbered transforms in
`sql/transformations/230–430` shape it into load-ready `*_Load` tables (assigning
migration keys, resolving RecordTypes, wiring parent relationships, inheriting
designations, etc.), and `bulkops` pushes each to the org in dependency order.

## Prerequisites

1. The framework configured per the top-level `README.md` (a `.env`, the
   `SF_Migration` mirror DB, the venv).
2. A **target org alias** (`SF_ORG_ALIAS`) pointing at a scratch/sandbox org you
   may safely load into.
3. The `MigrationID__c` external-id fields + field-level security deployed to
   that org (`force-app/main/default/objects/*` and the `MigrationFieldAccess`
   permission set).
4. If the org isn't empty, wipe prior sample records first — see
   [Resetting a test org](#resetting-a-test-org-first).

## Generating the mock data — two paths

**A. Framework path (recommended).** Regenerates each recipe fresh from the
target org's live `describe()`, so field lists always match the org's real
schema (fields added/removed since these recipes were captured are handled
automatically). Run one call per build group that generates data:

```bash
.venv/Scripts/python.exe cli.py --org target generate-related-mock-data Account Contact --count Account=8 --count Contact=1-3
.venv/Scripts/python.exe cli.py --org target generate-related-mock-data Account --count Account=5
.venv/Scripts/python.exe cli.py --org target generate-related-mock-data Contact --count Contact=10
.venv/Scripts/python.exe cli.py --org target generate-related-mock-data ContactPointAddress --count ContactPointAddress=35
.venv/Scripts/python.exe cli.py --org target generate-related-mock-data ContactPointPhone --count ContactPointPhone=35
.venv/Scripts/python.exe cli.py --org target generate-related-mock-data ContactPointEmail --count ContactPointEmail=35
.venv/Scripts/python.exe cli.py --org target generate-related-mock-data Campaign CampaignMember --count Campaign=4 --count CampaignMember=3-8
.venv/Scripts/python.exe cli.py --org target generate-related-mock-data GiftDesignation --count GiftDesignation=6
.venv/Scripts/python.exe cli.py --org target generate-related-mock-data GiftCommitment --count GiftCommitment=15
.venv/Scripts/python.exe cli.py --org target generate-related-mock-data GiftTransaction GiftRefund GiftSoftCredit --count GiftTransaction=40 --count GiftRefund=0-1 --count GiftSoftCredit=0-1
```

**B. Standalone Snowfakery path.** Run the committed recipes directly — no live
org needed for generation (only for the later load). Useful for inspecting or
hand-editing the exact recipe:

```bash
snowfakery sample_data/recipes/01_household_accounts_and_contacts.recipe.yml --output-format csv --output-folder ./_out
# ...repeat per recipe, then load each CSV into its <Object>_Mock table.
```

Path A is the one this project itself uses; the committed `recipes/*.yml` are
exactly what Path A produces (captured here so a clone has the recipe in hand,
and so Snowfakery users can run it without the framework).

## Loading into the org — ordered sequence

Run the build groups **in order**. For each object with a `*_Load` table, apply
the standard per-object gates from `CLAUDE.md`'s "Standard workflow" before
loading — Hard Rule 6 (`add-bulk-load-sort-column`), Rule 7
(`check-load-table-duplicate-keys`), Rule 12 (`validate-external-id`) — then
`bulkops <Object> insert <Object>_Load --external-id MigrationID__c
--email-deliverability <what Setup shows>`.

1. **Household Account + Contact** → run `230`, `240`, load Account then Contact.
2. **AccountContactRelation / PartyRelationshipGroup / ContactContactRelation**
   → `250` (no-op — ACR is auto-created), `260`, `270`. Replicate the fixed
   `PartyRoleRelation` reference set first.
3. **Organization Account** → `280`, load.
4. **Person Account** → `290`, load.
5. **ContactPoint Address / Phone / Email** → `300`, `310`, `320`, load each.
6. **Campaign + CampaignMember** → `330`, `340`, load.
7. **GiftDesignation** → `350`, load.
8–9. **GiftCommitment (+ Schedule)** → `360`, load; then `370` **replicates**
   `GiftCommitmentSchedule` and inserts only genuinely-missing schedules.
10. **GiftTransaction + GiftRefund + GiftSoftCredit** → `390`, `400`, `410`, load.
11. **GiftDefaultDesignation + GiftTransactionDesignation** → `420` (no-op — GDD
    is auto-created), then **replicate** `GiftDefaultDesignation` and
    `GiftDesignation --raw`, and run `430`, load.

The mid-stream `replicate` steps (schedules before group 10, designations before
group 11) exist because the platform auto-creates those child records on parent
insert — the transforms read the real auto-created rows rather than inventing
them. See `validators/GiftCommitmentSchedule.md`,
`validators/GiftDefaultDesignation.md`, and
`validators/GiftTransactionDesignation.md`.

## Expected results

Roughly: **13 Accounts** (8 household + 5 organization) + **10 Person Accounts**,
**~13 Contacts**, **105 Contact Points** (35×3), **4 Campaigns** / ~20
CampaignMembers, **6 GiftDesignations**, **15 GiftCommitments**, **40
GiftTransactions**, a handful of GiftRefunds/GiftSoftCredits, and **40
GiftTransactionDesignations** (one per transaction, inheriting the parent's real
default designation).

**Counts vary slightly run-to-run** — the recipes use random ranges
(`Contact=1-3`, `CampaignMember=3-8`, `GiftRefund=0-1`) and Snowfakery/Faker is
not seed-pinned, so each generation yields fresh values with the same shape.
GiftRefunds and GiftSoftCredits are generated per-transaction but the transforms
**filter them to only the rows that satisfy the platform's real constraints**
(a refund's parent must be Paid, amount ≤ original, date ≥ transaction date), so
fewer land than are generated — realistic, since most gifts are never refunded.

## Resetting a test org first

To wipe a previous sample load and start clean, follow the live-verified
reverse-dependency sequence in
`okf/nonprofit-cloud/full-org-reset-between-build-attempts.md`. Every delete
there is a real live-org write — confirm the target org first (Hard Rule 2).
